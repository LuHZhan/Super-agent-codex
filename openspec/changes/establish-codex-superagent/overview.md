# SAC：第一版范围与方向

状态：需求澄清中。本文是人类阅读与修改入口；技术范围对应 `proposal.md`，CODING 接入设计对应 `design.md`。已确认 Open API 轮询起步，其他待决策项见下文；未开始实现。

## 1. 目标与范围

### 已确认

- **BASE-01 运行方式**：个人本地运行，使用本人 Codex 订阅额度，通过官方支持的认证与接入方式，遵守额度限制。现有 ChatGPT 登录下的 App Server 对话与跨进程恢复已实测，SAC 独立授权路径仍待验证。
- **BASE-02 Agent 角色**：Router 和 Worker 都由 Codex 承担。
- **BASE-03 主动性**：能够主动发现值得处理的工作，并在预设授权范围内启动和持续推进；不局限于用户逐项交办的任务。
- **BASE-04 参考关系**：参考 dsh-superagent-prototype（SAD）的实际实现，构建其 Codex 版本，统一简称 SAC；不要求以 dsh 为运行宿主。

### 已确认：SCOPE-01 先跑通明确 BUG 反馈单的信道闭环

先处理目标明确的 BUG 反馈单，跑通接收、分派处理及回传结果的信道闭环。例如“读取已有存档后角色位置错误”属于具体问题；“提高互动小说存档功能的可靠性”属于开放式目标，本阶段暂缓。

长期目标、开放式任务及主动发现工作的设计后续再讨论。此阶段划分不撤销 BASE-03 的长期产品目标，也不按任务执行时间机械区分是否纳入。

### 已确认：CHANNEL-01 首个接入平台

2026-11-02：用户确认首先接入腾讯 CODING 的 BUG 单。本轮调查 API、Webhook、SDK 并给出接入方案，不编写代码。

**REPO-01 仓库托管（已确认）**：用户确认代码仓库也在 CODING。BUG 来源与代码托管平台均为 CODING；SAD 的 GitHub 接入只作为实现参考。具体项目到仓库的映射、访问凭据及平台权限配置仍待明确；自动交付的产品授权见 AUTH-04。

## 2. 结构与流程

已确认的角色：Router 理解事件、判断是否需要行动并协调任务；Worker 承接具体任务并汇报结果或阻塞。

### 名称速查

完整定义统一维护在根目录 `GLOSSARY.md`，这里提供阅读提示：

| 名称 | 中文理解 | 在当前场景中的职责 |
| --- | --- | --- |
| Source | 事件来源 | 接收 BUG 单和评论的变化 |
| Thread | 事项会话 | 将同一 BUG 单及评论关联在一起 |
| Router | 路由与协调者 | 理解请求、判断处理方向并分派 |
| Worker | 执行者 | 处理任务，提供结果或阻塞原因 |
| Outbox | 待发箱 | 记录结果消息及发送状态 |
| Channel | 回传通道 | 将消息回复到原 BUG 单 |

这些名称描述职责，不代表必须拆成六个独立服务。

当前概念流程：接收明确 BUG 单 → 判断是否受理及授权 → 分派 Worker → 验证结果 → 回复原反馈单。它表达当前目标，不规定具体进程、存储、调度或通信协议。

参考 SAD 的实现区分：Source 接收事件，Thread 表示会话上下文，Channel 是回写到该会话的出口。用户所说的“信道部分”在本阶段覆盖接收和回传两端，不仅指 SAD 类型中的 Channel。该映射是参考实现事实，SAC 的最终接口尚未定稿。

### 已核对的 SAD 接入方式

- GitHub：SAD 启动 `gh` CLI 调用 API，轮询通知、Issue/PR 和评论等数据；回复也通过 API 写入原 Issue/PR。
- 飞书：SAD 启动 `lark-cli event consume` 子进程读取消息事件，并补读历史、轮询相关线程；回复通过 `lark-cli` 的消息回复命令发送。
- 内部：平台适配器将数据转换成统一 Trigger，并保存 Thread 和回写地址；输出先进入持久化 Outbox，再交给对应 Channel 发送。
- SDK 是调用平台 API 的一种代码封装，并不等于信道本身。SAD 在上述平台连接处主要调用 CLI；SAC 已选择 CODING Open API 轮询起步。
- 平台信道接入与 Codex 执行引擎接入是两条独立边界，不能用 Codex SDK 替代平台的消息接收、认证和回写能力。

### CODING 接入决定与配套建议

- **CONN-01 连接方式（已确认）**：第一版由本地 SAC 通过 HTTPS 调用 CODING Open API，定时读取缺陷及评论，结果通过 API 回写。Webhook 后置；后续引入时保留补偿读取。
- **CONN-02 适配边界**：CODING Client 处理认证和 HTTP；Source 适配器接收、去重并关联会话；Codex Router/Worker 处理任务；Channel 经 Outbox 回写原 BUG 单。保留 SAD 的职责划分，不照搬其 `gh` 命令。
- **CONN-03 受理边界（已确认）**：由 指定的 CODING 用户 在 CODING BUG 下评论 `@SAC xxxx` 作为受理信号；此前口令拼写已纠正。实现时匹配账号经验证的用户 ID，要求正文以独立 `@SAC` 开头并附非空指令。用户接受评论对同事可见；账号 ID 及富文本表示尚未核验。
- **POLL-02 处理人与指令权限（已确认）**　首版关注指定项目中分配给两名指定处理人中任意一人的 BUG，只有用户本人发出的有效 `@SAC` 指令才能触发任务。处理人按 `AssigneeId` 筛选，评论作者按 `CreatorId` 校验。联调时核对两人的 CODING 用户 ID。受理后转交给范围外处理人时按已确认的 D1 暂停、保留并继续跟踪。
- **POLL-01 首次监听与离线恢复（已确认）**　首版只监听你指定的一个 CODING 项目。从该项目首次开始监听时算起，之前发出的指令默认跳过。以后即使 SAC 离线，你也可以在新旧 BUG 单下发指令。恢复后 SAC 会在两名处理人的筛选范围内补读仍可读取的新指令，已受理的指令只处理一次。
- **INTAKE-01 受理前 BUG 已关闭（已确认）**　SAC 受理修复指令前发现 BUG 已关闭，就跳过修复，在本地面板注明「受理前 BUG 已关闭」。重新打开 BUG 后，你可以再发一条 `@SAC` 指令。
- **INTAKE-02 编辑已受理评论（已确认）**　SAC 按受理时的指令执行。之后编辑原评论不会改变任务或触发重跑。通过 CODING 调整范围时，请在原 BUG 单下新发一条 `@SAC` 指令。
- **INTAKE-03 指令语义（已确认）**　Router 结合当前任务理解 `@SAC` 后的自然语言。意思清楚时按授权范围执行。例如“继续修，先别推送”允许继续修复。若部分要求有歧义，先做明确允许的部分。只有下一步需要澄清时，SAC 才按 ATT-01 选择一个渠道提问。
- **PUSH-01 先别推送（已确认）**　以 SAC 受理这条指令时为准。还在排队的推送就地拦下，改动保留在本地。推送若已发出，SAC 核对 CODING 上的实际结果并显示在面板，查清前显示「推送结果待核对」。两种情况下都暂停创建 MR。
- **PUSH-02 恢复推送（已确认）**　“继续修”只恢复本地修复和验证。等你明确允许推送后才可推送，Router 结合当前任务理解你的意思，无需固定措辞。
- **UI-02 日常沟通（已确认）**　localhost 是你就某张 BUG 直接和 Codex 对话的入口。你在该任务里说“可以推了”，SAC 确认是你本人后，就解除这张单的推送限制，验证通过后推送。无需在 CODING 重复指令。原 BUG 单仍用于发起任务、受理和结果回评，以及必要时的一次提问。
- **PAUSE-01 修复中 BUG 已关闭（已确认）**　首次推送前发现 BUG 已关闭时，SAC 暂停原任务，保留 worktree 和已有改动。面板显示「修复中 BUG 已关闭，改动已保留」。你重新打开 BUG 并新发一条 `@SAC` 指令后，SAC 核对已有改动，再继续修复。
- **PAUSE-02 分支已推送、MR 未创建（已确认）**　这时发现 BUG 已关闭，SAC 暂停创建 MR，保留远端修复分支和本地 worktree。面板显示「BUG 已关闭，修复分支已推送，MR 未创建」。你重新打开 BUG 并新发一条 `@SAC` 指令后，SAC 沿用原分支，核对改动和验证结果后再创建 MR。
- **MR-01 评审中 BUG 已关闭（已确认）**　SAC 发现 BUG 已关闭时，自动关闭本次修复仍在评审中的 MR。
- **MR-02 重开 BUG 后再次评审（已确认）**　旧 MR 因 BUG 关闭而关闭后，你重新打开 BUG 并新发一条 `@SAC` 修复指令。SAC 沿用原修复分支，对照当前开发主分支核对改动，重新验证通过后新建 MR。
- **CONN-04 可靠性**：保存读取进度，重启后补读；评论单独检查，不能依赖其必然改变事项更新时间；发送结果不明时先核对远端，避免盲目重发。
- **CONN-05 回写范围**：已确认采用 SAD 风格的简短正常结果回评：一句包含用户可见结果、MR 链接及必要下一步，实质限制才补第二句；不描述技术内部，技术证据留在 MR 和内部报告；MR 达到可评审状态后再发结果评论，不把“已创建 MR”当作“已修复上线”。
- **CONN-06 认证**：优先验证项目令牌是否覆盖所需接口及回复身份；必要时使用受限账号的个人令牌。CODING 令牌与 Codex 登录分别管理，不把平台凭据放入模型上下文。

官方 API 已列出缺陷列表、详情、评论读写、附件地址、事项修改能力。Service Hook 支持事项创建、更新、状态和处理人变化等事件，但公开事件表未单独列出事项评论事件，不能据此假设评论变化必有通知。未找到可确认覆盖当前事项接口的官方 Node.js/TypeScript 或 Python SDK；建议先实现薄 HTTP Client。完整证据与限制见 `design.md`。

### 首轮工程方案（2026-11-05 整理，工程建议）

**ENG-01 接入方式**　建议本地 SAC 后台通过 Codex App Server 管理一个 Router 会话和每张 BUG 的独立 Worker 会话。你在 localhost 查看任务、回答问题，后台负责轮询、保存状态和调度。首轮建议一个 App Server 进程承载这些会话，Worker 仍按已确认的 3+1 规则运行。官方文档将持续对话、进度事件和审批列为 App Server 的用途，当前仍有实验性限制。[官方架构说明](https://developers.openai.com/blog/codex-as-a-platform) · [接口成熟度说明](https://learn.chatgpt.com/docs/mcp-server)

**AUTH-05 订阅接入**　新建 SAC 优先验证官方 Sign in with ChatGPT 的订阅授权流程。你为 SAC 授权后，后台使用本应用的凭据连接本地 Codex。官方专题覆盖本地托管应用使用 ChatGPT plan 的场景，因此这个方向有公开支持依据。具体账号、地区、授权和模型能否使用仍需联调确认。官方没有提供“绝不封禁”的承诺，使用仍需遵守账号、额度和使用政策。[官方适用范围](https://developers.openai.com/siwc/token-sharing-open-source) · [使用条款](https://openai.com/policies/terms-of-use/)

**AUTH-05 能直接用 CLI 登录吗？（2026-11-06）**　技术上可行。官方插件 codex-plugin-cc 让本机 Codex 管理登录和续期，订阅用量计入用户账号。Symphony 展示了如何从工单启动 Codex。官方对沿用 App Server 登录的说明明确覆盖已有本地或开源应用，对新建 SAC，公开文档依据更明确的路径仍是由你给 SAC 单独授权使用 ChatGPT plan。[插件说明](https://github.com/openai/codex-plugin-cc#codex-integration) · [Symphony](https://github.com/openai/symphony/blob/main/elixir/README.md) · [认证适用范围](https://learn.chatgpt.com/docs/app-server#auth-endpoints)

若进一步评估 CLI 托管登录，建议在 SAC 专用目录启动独立 CLI，由你用同一账号登录一次。Codex 保存并刷新该次登录，SAC 只检查登录类型。这样能分开本机凭据、会话和数据库，桌面与 SAC 仍共用账号额度。上一次测试证明已有登录能完成推理和恢复对话，专用目录首次登录、自然续期及桌面并行使用仍待验证。两种授权方案的验收条件见 design 第 9.2 节。

OpenAI 把 T3 列为开源集成。T3 Code 允许用户在应用内授权订阅，也支持手动接入已有 CLI 登录。SAC 首版可参考前一种体验，由你在 OpenAI 页面单独授权 SAC 使用订阅额度，桌面 CLI 继续管理自己的登录。本人账号的可用额度由两端共享。[OpenAI 对登录与额度授权的说明](https://learn.chatgpt.com/docs/sign-in-with-chatgpt) · [T3 Code 的两种接入方式](https://github.com/pingdotgg/t3code/blob/main/docs/user/providers-codex.md)

新的订阅授权由 SAC 管理续期。按官方提供的接入方式，换新 token 后需重启 App Server，再恢复原会话。额度不足时保留排队任务并等待可用，授权或政策拒绝时在 localhost 显示原因。共享账号、绕过限流等行为受条款限制。当前 3+1 表示任务并发能力，所有模型工作共享你的额度。[订阅接入与续期](https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server) · [额度说明](https://help.openai.com/en/articles/9793128-about-chatgpt-pro-tiers)

**REC-01 提问与继续**　建议 Worker 遇到缺信息时结束当前轮次，SAC 保存问题并显示在原任务里。你回答后，SAC 先保存答复，再让同一 Worker 会话继续。关页或重启后，仍从保存的问题和答复接上。后台工作已结束的等待任务会释放名额，让其他 BUG 推进。

**REC-02 恢复边界**　Codex 保存模型会话，SAC 保存 BUG 任务、授权、待答问题和投递记录。重启后先核对这些记录与实际执行情况，再续办。如果答复已经发给 Codex 但确认消息丢失，面板显示待核对，后台查清后再决定是否重发。历史丢失或执行状态不明时保留任务并显示阻塞。官方确认新订阅接入也支持本地会话恢复，完整链路仍待实测。[本地历史与恢复](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

**SEC-01 执行边界**　localhost 绑定本人访问，后台保管平台凭据，Worker 的文件和工具权限需要实际验证。首轮围绕 BUG、明确提供的资料和本地问答开展验证。账号凭据、SAC 状态库及其他任务工作区的隔离属于运行前检查。

这些是依据 SAD 与官方接口形成的工程建议。详细组件映射、接口差异、数据记录和验证步骤统一放在 design 的第 9 节。

## 3. 规则与边界

- 主动执行必须处于预设授权范围内；授权模型尚未确定。
- 工作范围与动作权限分开决定。允许关注一个仓库不自动等于允许合并、发布或对外发送消息。
- 当前只讨论和维护文档，尚未授权编写产品实现代码。
- 已确认的偏好：避免通过共享标签改变同事工作流；用户接受评论对同事可见。采用评论口令受理，不再以完全私密或无通知作为入口要求。
- 受理与动作授权分别检查：指定账号的明确修复指令按 AUTH-04 允许自动交付；分析类指令不扩大为修复或交付。合并、发布和关闭 BUG 由人工处理。

### AUTH-01：执行流程的已确认部分

对明确要求修复的指令，用户认可 SAC 自动排查、修复、验证；仅要求分析时不扩大成修改代码。这是未来产品的执行规则，当前仍不编写产品代码。

**BRANCH-01 开发基线与 MR 目标（方向已确认，细节待定）**：用户的开发主分支持续承接新需求，SAC 修复分支应基于这条开发主分支，MR 也指向它。不能默认从仓库 main/master 切出或向 main/master 提交 MR。自动交付权限见 AUTH-04；每个 BUG 的分支与工作目录隔离方式见已确认的 BRANCH-04。

建议路径：用户开发主分支 → BUG 修复分支 → MR 回用户开发主分支 → 可评审后回评。开发主分支的具体名称尚未提供。

**BRANCH-02 远端基线（已确认）**：以 CODING 远端已推送的开发主分支为准，记录开始修复时的提交；不自动纳入本地未提交或未推送的修改。

**BRANCH-03 基线推进（已确认）**：修复分支仅由对应 Worker 及其子 Agent 开发。采用提交 MR 前同步、进入 MR 后冻结的流程：在首次推送和创建 MR 前完成 rebase、差异检查与重新验证；MR 创建后，即使开发主分支继续推进，只要没有代码冲突，就不主动修改、rebase 或更新修复分支。用户明确要求出现冲突时处理冲突并追加提交。通过将最新开发主分支 merge 到修复分支、解决冲突、验证后普通 push 来实现；用户已接受增加一个包含冲突解决结果的 merge commit。不再将 MR 后持续 rebase 或 force-with-lease 列为默认方案。明确的新人工修改指令另行受理，不从普通上下文评论推导修改授权。

rebase 不自动 squash，也不能决定最终 MR 是否生成 merge commit。若开发主分支在 MR 后继续推进，通常不能仅靠 fast-forward 完成最终合并；本方案不会因此自动解除修复分支冻结。希望开发主分支最终每 BUG 仅一条提交时可另选 squash；若要求完整线性历史则需重新权衡同步规则。CODING 项目的可用合并方式与保护规则尚未核验，最终合并仍由人工执行。没有代码冲突不等于最新组合已经通过测试，面板保留验证所针对的提交；是否对组合结果做只读验证另行设计。

### UI-01 初版在哪里处理 BUG（已确认）

初版在 SAC 自建的 localhost 任务页里与 Codex 对话、查看进度和授权操作。长期希望能直接在官方 Codex 桌面聊天窗口处理同一张 BUG，具体接入方式待验证。

用户已认可自建 SAC 前端、复用 Codex 执行能力的方向，以本地 Web 面板作为主要查看入口。后台建议通过 Codex App Server 管理会话并接收执行事件；这里的 CLI 指 Codex CLI，不是另一个 GPT CLI 产品。本机版本兼容、现有 ChatGPT 登录下的对话与同线程恢复已实测；SAC 独立授权、完整面板与业务链路仍待验证。

面板按 BUG 展示负责的 Worker、当前阶段、最近活动、等待原因、验证结果和 MR；展开后再查看公开执行消息、命令输出与 diff。采用阶段和真实事件，不编造完成百分比；离线或事件中断标明状态未知。关闭页面不应结束后台任务，这是建议的产品行为。

SAD 已有 Harness Web 中的 Superagent 面板，可参考其“先看需要人处理的事，再看健康和历史”的组织方式。Codex 官方提供自建客户端的 App Server 接口，但本次未找到保证任意外部 Worker 自动进入桌面任务列表并实时可控的契约，不把桌面同步作为首版依赖。面板展示范围和人工干预能力仍待决定，查看权限不自动等于执行控制权限。

“桌面集成”不表示可以像修改 dsh 源码那样改造官方 Codex 桌面前端。需区分自建客户端（App Server）、受宿主约束的插件 UI（MCP Apps）和官方原生任务列表同步。插件 UI 有公开接口，但 SAC 在当前桌面版本中的本地连接、持续更新和会话控制能力仍需验证；当前只确认自建前端方向，尚未授权实现。

### HOST-01：按架构选择复用、适配或自建（原则已确认）

用户明确：不以尽量复用 Codex 为目标，也不将 SAC 限定为薄编排层。先明确职责、状态归属、权限与可靠性要求，再逐项选择复用、适配或自建；比较语义匹配、可验证性、耦合、长期维护及总体复杂度。合理的自建成本可以接受；极端复杂度或无法实现时调整方案。Codex 的现有能力是候选实现，不因其存在就必须使用。个人本地、官方接入、订阅额度及 Router/Worker 使用 Codex 的既定约束继续有效，改变这些约束需另行讨论。

当前职责建议：SAC 管理 CODING 接入、BUG 任务状态、受理与动作授权、调度、可靠消息投递、Outbox、Git/MR 流程和管理面板。这些业务机制有相当部分在 SAD 中也是由 SAD 自己实现。Router 的理解和分派判断仍由 Codex 承担；SAC 普通程序落实状态与权限约束。其余宿主能力按 HOST-01 逐项设计，不将此前能力映射表视为完整批准的分工。

**AUTH-02 分层权限（已确认）**：Codex 的执行权限与 SAC 的“允许修复、推送、创建 MR、回评”等业务动作授权分别约束，不能仅靠提示词。dsh 的工具限制和执行前拦截不能原样搬到 Codex；具体拦截位置与防绕过机制仍需设计。

**CONN-04 回写恢复原则（已确认，具体协议待定）**：恢复 Codex 会话不代表已知 CODING 评论是否回写；SAC 必须独立记录并核对远端状态。会话历史不能代替发送记录；发送结果不明时不能直接宣布成功或盲目重复发送。Outbox 字段、标记和核对流程仍按接口实测确定。

**AUTH-03 动作执行入口（已确认）**：Worker 提交推送、MR、回评请求，由 SAC 校验任务授权、目标及验证状态，再由受控组件执行并记录回执。已授权动作可自动执行，无需逐次人工确认；自动交付范围见 AUTH-04。凭据隔离及防止 Worker 绕过入口的实现方式继续设计。此处确认产品架构，不是授权当前会话操作远端。

**AUTH-04 自动交付范围（已确认）**：对于指定账号发出的明确修复指令，在仓库/分支映射和隔离策略已确认、授权校验及要求的验证通过后，SAC 自动推送任务修复分支、创建或更新指向用户开发主分支的 MR，并在可评审后回评结果，不逐次询问。合并、发布和关闭 BUG 留给人工。分析指令不扩大为交付；检查未通过、证据不全或存在需求歧义时不宣称可交付，展示具体阻塞。独立分支方式见已确认的 BRANCH-04；基线同步按 BRANCH-03 执行，正常结果回评遵循 CONN-05；受理确认按 ACK-01 发送。需要用户决定或补充材料时按 ATT-01 提问，其他异常通知权限待定。这是未来产品的默认规则，当前仍仅讨论和维护文档。

**BRANCH-04 任务隔离（已确认）**：用户另行 clone 一份专用于 BUG 修复的本地仓库，与日常开发 clone 分开；SAC 基于这份专用 clone，为每张已受理 BUG 的本次修复任务创建独立修复分支与 Git worktree，worktree 放在专用仓库下。基线仍取 CODING 远端已推送的个人开发主分支，MR 仍指向该分支。评审中的补充反馈沿用原分支和当前 MR。这是两个本地 clone 连接同一个 CODING 远端仓库，不是新增远端仓库或 fork。代价是额外磁盘、依赖准备和后续清理管理；worktree 不是权限沙箱。专用 clone 路径、worktree 子目录名、跨 BUG 依赖、其他重开场景和清理规则后续确定。当前不执行 clone 或创建 worktree。

## 4. 取舍与原因

CONN-05 正常结果回评（已确认）：参考 SAD，用一句同事式短消息表达用户可见结果、MR 链接及必要下一步。例如：

> SAC：读档后角色位置错误的修复已提交，MR 〈实际链接〉待评审。

采用上述短句，不采用此前自拟的三行固定格式。示例不是实际修复结果，必须达到已验证、可评审状态后才发送；有影响使用或交付的限制时才补第二句。技术证据留在 MR 或内部报告，不机械添加测试结果和“尚未上线”。

SAD 的回复分为受理确认、直接答问、结果通知和需要人工处理四类，并有发送条件与去重实现；常规进度留在内部。其“一句结果 + 链接”等详细短文案规则主要面向 IM，GitHub 另要求自动 Agent 身份声明并保持简洁。SAC 将该表达原则适配 CODING，明确修复请求的受理确认按 ACK-01 发送，人工提问按 ATT-01 处理，其他异常通知另行决定。

**MSG-01 评论署名（已确认）**　SAC 发到 CODING BUG 单的每条评论都以 `SAC：` 开头，让同事一眼看出是谁在说话。

按用户确认，优先以具体 BUG 单验证信道闭环，暂不引入开放式目标拆解和长期任务规划。

后续设计以 SAD 的实际代码和文档为依据，明确区分可以借鉴的机制与需要适配 Codex 的部分，不将其当作可直接更换模型配置即可运行的系统。

CONN-01 采用轮询的原因：个人本地运行不需要提供平台可访问的回调地址，容易断点恢复，也与 SAD 的 GitHub 接收方式接近。代价是通常要等待一个轮询周期，且需要控制 API 调用量。D2 已确认以约 60 秒为初始轮询间隔，按联调情况校准。

Webhook 可降低通知延迟，但需要平台可达的接收端、验签和投递补偿。它不替代读取详情和回写评论的 API。

CONN-03 采用评论口令的原因：直接在 BUG 现场表达指令，不需改变标签或处理人，同时限制只有指定账号能触发。SAC 必须轮询配置范围内尚未受理 BUG 的评论才能发现新指令，不能只轮询已有任务。

例如 指定的 CODING 用户 发送“@SAC 排查并修复读档后角色位置错误”，符合规则后交给 Router；其他人的同样文本不创建任务。本文示例不表示当前已获修复或推送授权。

## 5. 验收方式

**ACK-01 受理确认（已确认）**　指定账号的明确修复指令通过受理及权限检查，且任务已保存后，在原 BUG 下回复一次具体的确认，例如“SAC：已受理读档后角色位置错误的排查与修复。”这表示已接下请求，不表示已开始执行或完成；后台排队时也不谎称正在修复。对同一触发评论去重，普通轮询、重试不反复发确认。无效口令、其他作者或普通讨论不因此获自动回复。该规则适用于明确修复请求。

**ATT-01 需要你做决定或补充材料时（已确认）**　SAC 先查 BUG 描述、评论和已有材料。确实需要你回答才能继续时，默认在 localhost 对应 BUG 的任务对话里问。只有你明确为这张 BUG 指定在 CODING 提问时，才在原单下问。关掉页面或暂时未答，SAC 都沿用当前选择。同一个问题只选一处问一次。

**ATT-03 切换提问渠道（已确认）**　每张 BUG 的任务页可选「本地对话（默认）」或「原 CODING 单」。点选和用自然语言指定会更新同一个设置，只对之后的新问题生效。例如已经在本地问过复现步骤，再切到 CODING，这个问题仍在本地等你回答。受理确认和结果回评仍按原规则写回 BUG 单。

**ATT-02 直接回复（已确认）**　你在原 BUG 单下点「回复」，回答 SAC 的问题即可，无需再写 `@SAC`。例如你回复“点设置里的保存按钮”，SAC 确认是你回答了这条待答问题后，就用这条线索继续原任务。若无法确认回复对应哪条问题，任务保持等待。

**ACCEPT-01 第一轮信道验收（方案已确认，尚未实测）**　联调时由你提供一张 CODING 上已有、仍待排查的真实 BUG 链接。你在原单发 `@SAC` 并说明要排查什么，localhost 应出现一个对应任务。如果排查确实缺少信息，SAC 只在该任务对话里问一次。你在本地回答后，应能看到 SAC 在原任务里用上这条信息继续排查。代码修复和 MR 交付在下一轮验收，CODING 评论与直接回复的关联另行验证。

首轮工程验证先检查订阅授权、同线程重启续办、待答问题恢复、投递结果不明、3+1 调度及权限隔离，再用真实 BUG 验收。2026-11-05 已完成独立 CLI 配置兼容检查，以及现有 ChatGPT 登录下的同线程重启续办实测；SAC 独立 OAuth、业务问题恢复、去重、调度与隔离仍待验证。

接入建议的验证重点：重复读取不重复受理；人工追问关联原任务；SAC 自己的回评不触发新任务；离线恢复不遗漏仍可读取的更新；发送超时后核对远端；权限失效时明确报错；结果回到正确 BUG 单。CODING API 及账号尚未实测，不宣称链路已经跑通。
