# SAC 第一版范围提案

状态：草稿，需求澄清中。人类视图见 `overview.md`；待确认建议不得作为实现依据。本目录按项目约定手工建立，不表示 OpenSpec CLI 已安装或完成校验。

## Why

用户需要在预设授权范围内主动发现、启动并持续推进工作的个人助手。仅等待逐项指令或在一次请求中并行分工，不能满足已确认的主动性目标。

当前阶段先参考 SAD 的实现跑通目标明确的 BUG 反馈单信道闭环，长期目标与开放式任务后续处理。阶段目标不替代长期产品方向。

## What Changes

已确认的产品约束：

| 标识 | 约束 |
| --- | --- |
| BASE-01 | 个人本地运行，使用本人 Codex 订阅额度，通过官方支持的认证与接入方式并遵守限制；现有 ChatGPT 登录下的 App Server 对话及重启恢复已实测，SAC 独立订阅授权仍待验证 |
| BASE-02 | Router 与 Worker 均由 Codex 承担 |
| BASE-03 | 支持主动发现工作，并在预设授权范围内启动及持续推进任务 |
| BASE-04 | 参考 SAD 的实际实现，构建其 Codex 版本，统一简称 SAC；不要求依赖 dsh 作为运行宿主 |

### SCOPE-01：已确认

第一阶段处理目标明确的 BUG 反馈单，闭环为接收 → 受理与授权判断 → 分派 Worker → 验证结果 → 回复原反馈单。

“提高互动小说存档功能的可靠性”等开放式目标、长期任务规划及主动发现工作暂缓。是否纳入本阶段取决于任务目标是否明确，不仅取决于执行耗时。

该范围不直接授予具体执行权限；当前仍仅维护设计文档，不编写实现代码。

### CHANNEL-01：已确认

2026-11-02：首个平台为腾讯 CODING，接入其缺陷事项。用户授权本轮检索官方接口并给出方案，尚未授权实现或调用账号接口。

### CONN-01 与 REPO-01：已确认

用户认可第一版采用 Open API 轮询，Webhook 后置；同时确认代码仓库也托管在 CODING。SAD 的 GitHub 实现仅作参考，SAC 不以 GitHub 或 gh 为接入前提。

BUG 单与仓库的映射、仓库访问凭据、推送和 MR 权限仍需另行明确。领域名称统一记录在根目录 `GLOSSARY.md`，人类视图提供速查表。

## Capabilities

本阶段拟增加 `coding-bug-channel` capability，负责缺陷事件接收、上下文读取、会话关联及结果回写；具体行为规则待确认后形成 delta spec。

参考实现映射：SAD 的 Source 负责事件接收，Thread 表示会话，Channel 负责回写；参考 `src/sources/kind.ts` 和 `docs/008-cookbook.md`。SAC 的信道闭环覆盖输入与输出两端，采用 CODING Open API 轮询与回评，Codex 接口仍待确定。

已核对的连接实现（以下路径均相对 SAD 参考仓库）：

- `src/infra/commands.ts`：用子进程调用 `gh`、`lark-cli`，解析其 JSON 输出；`api` 封装配置仓库内的 GitHub API 调用。
- `src/sources/github.ts`：轮询通知、仓库事件流及订阅线程，维护游标。
- `src/sources/feishu-loops.ts`：启动 `event consume im.message.receive_v1 --as bot`，逐行解析输出，另行补读历史与轮询线程。该证据只确定 SAD 到 CLI 的连接，不推断 CLI 内部传输协议。
- `src/sources/github-channel.ts`、`feishu-channel.ts`：发送回复；前者通过隐藏消息标记检查既有回复，后者传入 idempotency key，降低重试重复发送风险。
- `src/app/outbox.ts`：持久化发送回执并调度重试，再通过 SourceRegistry 调用对应 Channel。

这些是 SAD 的实现事实。SAC 已确认采用 Open API 轮询起步，Service Hook 后置。平台消息适配与 Codex 执行引擎适配保持独立边界。

CONN-03 已确认：由 指定的 CODING 用户 在 BUG 下评论 `@SAC xxxx` 作为受理信号，用户纠正了口令拼写并接受同事可见。实现按经验证的用户 ID、正文开头独立口令及非空指令共同匹配；账号 ID 尚未核验。接收端要发现尚未受理 BUG 的新评论，不能只轮询已有任务。

**POLL-01 已确认。** 首版监听范围限于用户指定的一个 CODING 项目。保存该项目首次监听的起点和读取进度。默认跳过起点之前的指令，离线恢复时在 POLL-02 范围内补读期间发出的指令，包括旧 BUG 单上的新评论。

**POLL-02 已确认。** 首版监听分配给两名指定处理人中任意一人的 BUG，仅用户本人发出的有效 `@SAC` 指令可触发任务。按经核验的用户 ID 分别匹配处理人与评论作者。用户接受离线期间尚未受理且已转出范围的 BUG 可能漏读指令。D1 已确认已受理任务转出范围时暂停、保留并继续跟踪，等待用户决定。D2 已确认约 60 秒轮询。D4 已确认手动启动、关页后台继续、重启核对状态后恢复。D5 已确认故障集中显示在 localhost，短暂网络故障退避重试，需要人工处理时显示阻塞。D3 已确认默认 3 个普通 BUG Worker 执行名额，上限可配置，超出排队。人工消息唤醒已有任务可使用 1 个额外名额，默认最多同时执行 4 张 BUG，人工续办优先于新任务。等待答复且无后台工作时释放名额，Router 和子 Agent 的资源另行计量。

**INTAKE-01 已确认。** 在线轮询和离线补读都在受理修复指令前核对 BUG 当前状态。已关闭则跳过，并在本地面板注明「受理前 BUG 已关闭」。重新打开后，由用户发出新的 `@SAC` 指令触发受理检查。

**INTAKE-02 已确认。** 受理时保存指令正文。已受理评论的后续编辑不改变任务或触发重跑，通过 CODING 调整范围时，以同一 BUG 下新发的 `@SAC` 指令受理。

**INTAKE-03 已确认。** Router 结合当前任务理解受理指令的目标和限制，SAC 先执行明确获准的工作。歧义影响下一步时，才按 ATT-01 选择一个渠道提问。

**PUSH-01 已确认。** 受理「先别推送」时，拦下尚未发出的推送并保留本地改动。对已发出的推送核对远端结果并在面板显示，暂停创建 MR。

**PUSH-02 已确认。** “继续修”仅恢复本地修复和验证。推送限制持续到用户明确许可，Router 按语义识别。

**UI-02 已确认。** 用户通过 localhost 中对应 BUG 的 Codex 任务对话沟通。本人在此明确允许推送即可解除该任务的推送限制，验证通过后执行，无需通过 CODING 重复授权。原 BUG 单的任务触发、回评及必要提问规则继续适用。

**PAUSE-01 已确认。** 已受理任务在首次推送前发现 BUG 已关闭时暂停，保留原 worktree 和改动，在本地面板注明「修复中 BUG 已关闭，改动已保留」。BUG 重新打开且用户新发有效 `@SAC` 指令后，核对已有改动并继续原任务。

**PAUSE-02 已确认。** 修复分支已推送、MR 尚未创建时，若 BUG 已关闭，暂停创建 MR 并保留远端分支及本地 worktree。重新打开 BUG 并收到新的有效 `@SAC` 指令后，核对原分支的改动和验证结果，再继续创建 MR。

**MR-01 已确认。** 若 BUG 已关闭，SAC 有权关闭该任务关联且仍在评审中的 MR。

**MR-02 已确认。** 前一轮 MR 因 BUG 关闭而关闭后，须由用户重开 BUG 并新发有效 `@SAC` 修复指令。SAC 复用原修复分支，核对改动，重新验证通过后新建指向个人开发主分支的 MR。

AUTH-01 已确认明确修复指令允许自动排查、修复和验证；分析类指令仍只分析。自动交付范围见已确认的 AUTH-04；分支隔离方式见已确认的 BRANCH-04，不视为本轮实际操作授权。

BRANCH-01 方向已确认：修复基于用户持续开发新需求的开发主分支，MR 目标也为该分支，不默认使用仓库 main/master。BRANCH-02 已确认：从 CODING 远端已推送版本取得基线，不自动纳入本地未提交或未推送改动。

BRANCH-03 已确认：各修复分支只由对应 Worker 及其子 Agent 开发；首次推送/MR 前 rebase 并验证，MR 后无代码冲突即冻结，不因目标分支推进持续 rebase。出现冲突时追加提交解决，采用 merge 最新目标到修复分支、解决冲突、重新验证后普通推送；用户已接受新增 merge commit。撤销 MR 后自动 rebase 和 force-with-lease 的默认建议。明确人工修改指令另行受理；验证证据保持对应 SHA，不能以无冲突代替新组合验证。最终 MR 合并方式和 CODING 保护规则另行确定。

UI-01 自建前端方向已确认：初版以 SAC 自建 localhost 任务页为对话与进度入口，复用 Codex 执行能力。建议展示 BUG、Router/Worker 状态、等待原因、验证和 MR，技术执行细节按需展开；后台通过候选 Codex App Server 接口接收事件并维护状态，页面关闭不结束任务。参考 SAD 面板的信息组织，长期目标是直接在官方 Codex 桌面聊天窗口处理 BUG，接入方式待验证。独立 CLI 配置兼容、现有 ChatGPT 登录及同线程重启恢复已实测；SAC 独立授权、前端和控制权限仍待验证，未授权产品实现。

HOST-01 原则已确认：按架构职责、状态归属、权限、可靠性、耦合和总体维护成本，逐项决定复用、适配或自建，不以尽量复用为目标，不把 SAC 限定为薄编排层。合理自建成本可接受，极端复杂度或无法实现时调整方案。个人本地、官方接入、订阅额度和 Router/Worker 使用 Codex 的约束继续有效；此前宿主能力映射仍是候选方案。

AUTH-02 已确认：Codex 执行权限与 SAC 修复、推送、MR、回评等业务授权分别约束，不仅靠提示词；dsh 工具 guard/restrict 需要适配。CONN-04 回写恢复原则已确认：SAC 独立记录并核对 CODING 评论回写状态，不能以恢复 Codex 会话代替业务回执恢复。具体权限机制和回写协议仍待确定。

AUTH-03 已确认：Worker 请求推送、MR、回评，由 SAC 受控组件校验并执行，统一维护授权和回执；已授权动作无需逐次确认。自动交付范围见 AUTH-04，凭据隔离与防绕过方式后续明确，不表示当前会话实际远端操作已授权。

AUTH-04 已确认：明确修复指令预先授权验证通过后的推送任务修复分支、创建/更新指向个人开发主分支的 MR 及可评审后的结果回评；合并、发布和关闭 BUG 留给人工。依赖仓库/分支映射、隔离策略和相关校验明确；分析请求不扩大范围，验证不足或需求歧义保持阻塞。基线同步按 BRANCH-03 执行，正常结果回评按 CONN-05 执行；受理确认按 ACK-01 发送。需要用户决定或补充材料时按 ATT-01 提问，其他异常通知权限待定。当前仍不实现或执行远端操作。

BRANCH-04 已确认：用户另行 clone 一份 BUG 修复专用本地仓库，SAC 以此创建各 BUG 修复任务的独立分支和 worktree，worktree 位于专用仓库下，不挂在日常开发 clone 上。两个 clone 对应同一 CODING 远端，修复基线及 MR 目标仍为个人开发主分支；任务内补充反馈复用原分支及 MR。不将 worktree 当权限沙箱；路径、依赖准备、跨任务依赖、重开与清理规则后续确定。本轮不执行 clone 或创建 worktree。

CONN-05 已确认采用 SAD 风格的正常结果短通知，评论不描述技术内部。按该原则，将用户可见结果、MR 链接和必要下一步写回 BUG，将技术证据放在 MR/内部报告。正常结果回评在 MR 可评审后发生，不以 MR 创建成功等同于完成、合并或上线。

建议方案及证据见 `design.md`，与人类视图使用 CONN-01 至 CONN-06 对应。尚无已建立的主规格可供修改，暂不创建 delta spec 或实施 tasks。

CONN-05 正常结果回评文案已确认：参考 SAD 的短通知原则，一句表达用户可见结果、实际 MR 链接和必要下一步，实质限制才补第二句；示例见 overview。此前三行格式是 SAC 自拟候选，不是 SAD 原有模板。SAD 有受理确认、答问、结果和人工介入四类回复的发送条件与去重；SAC 的其他回复类别及字数限制另行决定。

**MSG-01 已确认。** SAC 发到 CODING BUG 单的所有评论统一以 `SAC：` 开头。

### 首轮工程核验更新（2026-11-05）

认证优先验证官方 Sign in with ChatGPT 的本地应用订阅授权路径。官方文档覆盖这一使用场景，账号准入和模型请求仍需实测，遵守账号、额度及使用政策是接入条件。公开文档没有提供账号免封保证。App Server 的实验性限制和新授权的令牌续期责任已记录。[订阅接入范围](https://developers.openai.com/siwc/token-sharing-open-source)

2026-11-06 对照 codex-plugin-cc 与 Symphony 源码后，保留“专用状态目录中由 Codex 管理本人 CLI 登录”作为技术候选。它可减少 SAC 对令牌的管理，共享的账号额度及新应用的政策适用范围仍需考虑。首选应用授权及候选 CLI 登录的隔离方式、验证顺序和已知证据见 design 第 9.2 节。当前处于方案比较阶段。

按用户授权，独立 npm CLI 已由 0.130.0 更新至 0.166.0；原配置副本通过严格检查，已解决 service_tier = "default" 的解析错误。隔离测试以现有 ChatGPT 登录完成两轮 gpt-6-astra 请求，新进程通过 thread/resume 恢复相同线程并准确使用先前信息。新版核心 schema 已重新检查。桌面/VS Code 原运行时未停止，原配置与登录文件校验一致。SAC 独立 OAuth、令牌续期、权限边界、业务恢复及 CODING 联调仍待验证，不能将单线程实测扩大为 SAC 已可运行。

## Impact

**ACCEPT-01 分轮验收（已确认，尚未实测）**　第一轮选用 CODING 上已有的真实 BUG，验收从原单指令到唯一对应的 localhost 任务，以及一次真实的本地提问、答复和原任务续办。如果材料已经足够，该单只验证实际走到的步骤，问答环节仍待验证。下一轮验收代码修复和 MR 交付，CODING 评论与直接回复的关联另行验证。

**ACK-01 已确认。** 明确修复请求通过受理与权限检查、任务持久化后，在原 BUG 下一次性确认已接下具体工作；按触发评论去重，不把排队描述成正在执行，不发送例行进度。

**ATT-01 已确认。** 现有资料不足、下一步需要用户决定或补充材料时，默认在 localhost 对应 BUG 的任务对话提问。第一版按 BUG 单独指定，只有用户明确为该 BUG 选择 CODING 时才在原单提问。关闭页面或等待超时均不触发切换。两个渠道共享同一待答问题，每个问题只问一次。

**ATT-03 已确认。** 每张 BUG 单的渠道选择控件与自然语言指令共享提问设置。切换只影响之后的新问题，已有待答问题继续在原渠道等待。

**ATT-02 已确认。** 指定账号直接回复原 BUG 单下 SAC 的待答问题即可补充原任务，无需重复 `@SAC`。关联明确且答复足以继续时，在原授权范围内恢复。

当前维护设计讨论文档；用户另行授权的独立 CLI 升级与隔离恢复核验已完成。未修改两个参考仓库、未安装 SAC 产品依赖、未编写产品实现代码。临时诊断脚本和测试状态在核验后清理，不作为 SAC 实现提交。

后续需要评估认证接口、额度与并发、持久化、恢复及授权机制；本提案不将这些未验证内容表述为已经具备的能力。
